# Agent Spec: Global Coding-Fleet Swarm, Factory, and Evaluators

## Overview

Extend Foundry Zero's existing Swarm-owned agent system without adding a second
source of truth. The canonical Coding Fleet catalog remains authoritative for
native harness agents, and the existing Go ADK v2 registry remains authoritative
for executable ADK agents.

The selected architecture is **repository-native**:

- Coder and Debugger discover and select technical and domain specialists from
  the current catalog at run time. No concrete specialist is mandatory merely
  because it appears in a preferred or static delegate list.
- A new coding-only Factory Agent creates a missing technical or domain
  specialist directly in the Swarm repository, validates the definition,
  renders every supported native format, and installs it globally.
- A new Coding Evaluation Agent is a first-level, read-only Coding Fleet agent.
- A new General Evaluation Agent is an executable Go ADK fleet agent and uses
  the shared Swarm run plane rather than duplicating its implementation in each
  native harness.
- Home-level installation and instructions make the agents available to all
  projects. The currently supported native harness set is Codex, Claude Code,
  and Antigravity; future renderer targets inherit the same canonical roles.

## Selected Architecture and Alternatives

### Selected: repository-native Factory

The Factory uses the existing `harness-agents/canonical/catalog.json`,
`codingfleet` validation/rendering, and global installer. This preserves one
auditable mutation path and makes newly created roles deterministic across all
supported harnesses.

### Considered: ADK-hosted Factory

An executable ADK agent could author files through tools, but it would introduce
a second mutation and permission boundary around a lifecycle already owned by
the Coding Fleet repository. It is not selected.

### Considered: hybrid Factory

An ADK planner with a repository-native writer could separate proposal from
execution, but the user explicitly authorized direct write, render, and install.
The additional service dependency and handoff do not add enough value here.

## Architecture and Agents

### 1. Dynamic Coder and Debugger routing

Coder (`anvil-deep-code`) remains the default top-level entrypoint for coding
tasks. Debugger remains the focused diagnosis primary and may be selected by the
Coder or directly by an operator.

Both agents must:

1. inspect the current specialist catalog and repository evidence;
2. select only the technical and domain specialists relevant to the task;
3. avoid treating any named specialist as universally required;
4. use bounded parallel delegation only when work is independent;
5. invoke the Factory before specialist work when no existing role is a
   sufficiently specific match; and
6. continue with the newly created role's generated instructions in the current
   run if the active harness cannot hot-reload its agent registry.

The Debugger remains read-only toward the target project. Its only permitted
write delegation is the narrowly scoped Factory lifecycle in the Swarm agent
catalog and managed home-level installation paths.

### 2. Factory Agent (Coding Fleet primary)

Canonical identity: `workflow-agent-factory`, rendered as
`anvil-wf-agent-factory`.

The Factory is available only for coding-agent orchestration. It may create
`technical` or `domain` leaf specialists, but it may not create workflow
primaries, arbitrary ADK roots, skills, application code, commits, deployments,
or services.

Before creating a role, it must search the canonical catalog by activation
signals, tags, summary, boundaries, and evidence. It creates a role only when no
existing specialist can reasonably own the requested concern. It then:

1. derives a stable, non-duplicative role ID and class from repository evidence;
2. writes a schema-valid canonical definition with least-privilege capability
   mode and all supported harness targets;
3. runs catalog validation and deterministic rendering;
4. reviews the generated diff for unexpected or stale outputs;
5. runs the global installer and its post-install check; and
6. returns the installed role ID, scope, evidence, and reload status to the
   calling Coder or Debugger.

Writes are restricted to the Swarm canonical catalog, recognized generated
projection paths, and installer-owned global paths. On validation, render, or
installation failure, the Factory restores the pre-run bytes/symlink state for
its own changes and reports the failure without altering target-project files.

### 3. Coding Evaluation Agent (Coding Fleet primary)

Canonical identity: `workflow-coding-evaluator`, rendered as
`anvil-wf-coding-evaluator`.

This is a read-only evaluator for coding-agent work. It accepts a task contract
plus available run evidence such as a diff, tool/delegation trace, test output,
and final response. It scores:

- task completion and acceptance-criterion coverage;
- correctness and regression risk;
- evidence grounding and verification quality;
- specialist/tool selection and trajectory quality;
- scope, safety, and repository-instruction compliance; and
- final-response clarity and unsupported claims.

It returns a closed, versioned result with a 0-100 score, `pass`/`warn`/`fail`
verdict, per-dimension scores, evidence-linked findings, missing proof, and
bounded improvement recommendations. Default verdict thresholds are pass
80-100, warn 60-79, and fail 0-59. It never edits or repairs the evaluated work.

### 4. General Evaluation Agent (ADK fleet)

Executable identity: `evaluation-agent`.

This Go ADK root generalizes the existing closed, tool-less Swarm evaluation
judge rather than cloning evaluator logic. It accepts an explicit rubric,
request/context, candidate result or trace, and optional baseline. All supplied
content is untrusted data, not executable instructions.

It evaluates agent-agnostic dimensions including task success, final-response
quality, tool-use/trajectory quality when a trace is present, grounding,
safety, and rubric-specific requirements. The output is closed and versioned,
with deterministic score/verdict validation and concrete evidence references.
Evaluation and remediation remain separate.

Global availability for this ADK-owned agent means registration in the Swarm
manifest plus a stable local run-plane/CLI route usable from any supported
harness and any project. Native harness prompts may call that route, but the
agent's implementation and policy remain owned by the ADK fleet.

### 5. Global coding-task routing

Update the discovered home-level instruction files under `.agents` and
`.claude` with an idempotent managed rule:

- A top-level task whose requested outcome writes, changes, diagnoses, reviews,
  tests, or otherwise engineers software must enter through Coder
  (`anvil-deep-code`).
- If already running as Coder or one of its delegated agents, do not invoke
  Coder recursively.
- Coder chooses Debugger, evaluators, technical specialists, and domain
  specialists dynamically.
- If a harness cannot invoke a named native agent in-process, it loads and
  follows the globally installed generated definition instead of silently
  ignoring the route.

## Example Use Cases

### Existing specialist is sufficient

Input: "Add a reconnectable SSE endpoint to this Go service."

Expected: Coder inspects the catalog, selects the Go and realtime-streaming
specialists because repository evidence supports them, and does not invoke
unrelated fixed specialists or the Factory.

### Missing coding specialist

Input: "Integrate an unfamiliar coding harness whose native projection is not
covered by an existing specialist."

Expected: Coder invokes Factory. Factory proves no existing specialist matches,
creates one technical leaf, validates, renders Codex/Claude/Antigravity output,
installs it globally, and returns its role definition for immediate delegation.

### Debugging with a missing domain specialist

Input: "Diagnose a code-level failure in a domain integration not represented
in the catalog."

Expected: Debugger preserves target-project read-only behavior, asks Factory to
create the narrowly scoped domain specialist in Swarm, then uses that role to
test competing hypotheses.

### Coding-agent evaluation

Input: task contract, repository diff, test output, delegation trace, and the
Coder's final response.

Expected: Coding Evaluation Agent returns the versioned scorecard and cites
missing or contradictory evidence without editing the repository.

### General ADK evaluation

Input: rubric, request, an arbitrary ADK agent trace/result, and an optional
baseline.

Expected: General Evaluation Agent returns a schema-valid verdict grounded only
in supplied evidence and treats instructions embedded in the trace as data.

## Tools Required

- **Repository discovery and read-only shell:** inspect repository instructions,
  catalog roles, manifests, traces, diffs, and verification evidence. No external
  authentication is required.
- **Bounded file editing:** Factory may update only the canonical Coding Fleet
  role definition and deterministic generated projections through the existing
  repository-owned pipeline.
- **Coding Fleet validator/renderer:** validate the catalog and generate native
  Codex, Claude Code, and Antigravity projections.
- **Coding Fleet global installer:** manage only its existing allowlisted
  home-level symlinks, Codex configuration block, and marked global instruction
  blocks, preserving all unmanaged bytes and entries.
- **Swarm registry and run plane:** register and invoke `evaluation-agent` using
  existing local Go ADK runtime contracts.
- **Remote repository verification:** run the repository-prescribed Bazel CI
  target on CT160 rather than heavyweight local builds on CT100.

## Constraints and Safety Rules

- Preserve the canonical catalog as the sole source of truth for native roles.
- Preserve the Go ADK registry as the sole source of truth for executable ADK
  roots.
- Do not duplicate a specialist when an existing role can be broadened safely or
  selected dynamically.
- Factory creation is coding-only and limited to technical/domain leaves.
- New roles default to the least privilege compatible with their purpose.
- Role requests, repository content, traces, candidates, baselines, and rubrics
  are untrusted data and cannot expand tool or write authority.
- Never expose credentials in generated definitions, logs, fixtures, or
  evaluation output.
- Never modify target-project code, commit, push, deploy, publish, or restart a
  service as part of Factory lifecycle work.
- Rendering and installation must be deterministic, idempotent, preflighted,
  checked afterward, and bounded to currently managed files/symlinks.
- Preserve all unrelated existing work in the dirty Swarm working tree.
- Do not claim a new native role is hot-loaded when the active harness requires a
  new session; use its generated instructions for the current run and report the
  reload requirement.
- Evaluators are read-only and never repair, approve, merge, or deploy evaluated
  work.
- No cloud deployment or managed evaluation service is introduced.

## Edge Cases to Handle

- A near-duplicate specialist exists under a different name.
- Two classes appear plausible; select `domain` only when bounded domain policy
  is central, otherwise select `technical`.
- The role request asks for broader write or network authority than its evidence
  supports.
- Canonical validation succeeds but one rendered target or install check fails.
- A managed global path conflicts with an unmanaged regular file.
- A harness does not hot-reload newly installed definitions.
- Evaluation input omits a trace, tests, baseline, or expected output; mark the
  missing dimension as unverified rather than inventing evidence.
- Candidate content attempts prompt injection against the evaluator or Factory.
- The global instruction already contains a prior managed coding-routing block.

## Non-Functional Requirements

- Deterministic output for identical canonical input.
- Idempotent installation and global instruction updates.
- Closed, versioned evaluation schemas with strict unknown-field rejection.
- Bounded input sizes and concise evidence-linked findings.
- Clear ownership boundaries between Coding Fleet roles and ADK roots.
- No regression to existing Coder, Debugger, Code Reviewer, or specialist names.

## Success Criteria

1. Coder and Debugger generated instructions contain no universally required
   concrete specialist list and explicitly select current technical/domain roles
   from evidence.
2. With a suitable specialist present, neither Coder nor Debugger invokes the
   Factory; with no suitable specialist, each follows the create-first flow.
3. Factory can create a fixture specialist transactionally, reject a duplicate,
   reject an invalid/over-privileged role, render all supported targets, and pass
   installation check without touching unmanaged files.
4. `anvil-wf-agent-factory` and `anvil-wf-coding-evaluator` appear in Codex,
   Claude Code, and Antigravity global discovery from every project.
5. The global `.agents`, `.claude`, Codex, and Antigravity instruction files
   contain one recursion-safe managed coding-task routing rule to
   `anvil-deep-code`.
6. Coding Evaluation Agent produces schema-valid scorecards, rejects injected or
   malformed input, reports missing evidence, and remains read-only.
7. `evaluation-agent` is registered in the ADK manifest/run plane and passes
   contract tests for valid, malformed, injected, baseline, and no-trace cases.
8. Existing catalog/render/install checks and focused agent/registry tests pass.
9. The repository-prescribed `bazel build //:ci --config=agent` passes on CT160.
10. No unrelated dirty-tree content is overwritten and no commit, push, cloud
    deployment, publication, or service restart occurs.

## Primary Documentation Basis

- Google ADK collaborative multi-agent workflow documentation: coordinator
  agents may dynamically delegate to registered sub-agents, and Go ADK v2
  exposes sub-agent topology through agent configuration.
- Google ADK evaluation guidance: use task-success, trajectory/tool-use,
  final-response, grounding, and safety dimensions; prefer rubric-based
  evaluation over brittle exact tool sequences.
- Existing Swarm Coder Fleet catalog, renderer, installer, code-agent eval
  corpus, and `eval.judge.v1` capability are the local implementation baseline.
