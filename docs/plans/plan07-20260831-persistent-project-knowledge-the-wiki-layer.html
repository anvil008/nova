Persistent project knowledge — the wiki layer

Nova forgets. A review-fix loop runs up to ten fresh multi-lens reviews and ends by handing a branch to a human; the next loop on the next branch rediscovers the same finding from scratch, and a stalled ending — the most informative result the loop produces — leaves nothing behind at all. This milestone lands the smallest useful slice of a WikiSkill-style persistent knowledge layer: the mechanism ships here, the data lives in one global store namespaced per project, and a project that never opts in behaves exactly as it does today.

Storage (revised). The store is $NOVA_WIKI_HOME, defaulting to ~/.nova/wiki/, with one namespace directory per project: ~/.nova/wiki/<project-key>/. The earlier per-repository .nova/wiki/ layout is dropped. Namespacing is absolute — there is no flat shared wiki and no cross-project namespace in v1. Two facts found while investigating are worth stating rather than assuming: ~/.nova/ does not exist today (the home-level roots this repository uses are ~/.local/bin, ~/.claude, ~/.codex, ~/.gemini, and ~/.agents), so this milestone creates it; and the only environment-variable precedent is NOVA_EVAL_TASK_DIR, so the override is named NOVA_WIKI_HOME to match.

Project key (the new design point). wiki.py key --repo <path> resolves a target repository's *primary* toplevel exactly as nova-ws does — through .jj/repo for a secondary jj workspace, through the first git worktree list --porcelain entry for git — so every build per-issue workspace of one repository answers with one key. From that toplevel the key is the normalized origin remote (github-com-anvil008-nova; git@github.com:anvil008/nova.git and https://github.com/anvil008/nova collapse to the same key), falling back to <toplevel-basename>-<8 hex of sha256 of the resolved absolute toplevel> when there is no remote. Either way the key is reduced to the character class nova-ws already enforces for a key part — [a-z0-9][a-z0-9-]*, no slash — so a wiki key and a workspace key obey one spelling rule. Collisions are refused rather than resolved: each namespace records the source it was created from in project.json, every later command re-resolves and compares, and a mismatch is refused by name instead of silently sharing or silently forking a namespace. Renaming or retiring a namespace is a human act, like entering eval mode.

What the move buys and costs. The paper's ablation — the inference agent is denied wiki access — now holds trivially: the store is outside every repository, so no working copy, no build workspace, no diff, and no scored eval patch can contain it. Knowledge also compounds across every clone and workspace of one project rather than per checkout. The residual moves: the wiki is now per machine and per user rather than per team (R-01), and because it sits outside the repository the harness's own permission model is the only thing between an agent and the store (R-07). Read-only investigation confirms Nova's own gates do not stand in the way: build-guard has no outside-repository write rule — its only path denials are the eval marker and RAM-backed build target directories — and tdd-guard's sealed-path check returns false for any path outside the repository, so no guard change is needed, exactly as scoped.

Unchanged from the approved shape. No proposer and no validation gate; no new agent and no new handoff mode — consolidation is one documenter dispatch; hooks on review-fix-loop's three stop statuses plus record-only on an accepted build wave; a repository in eval mode is refused, now checked against the *target* repository the namespace was resolved from. The two-layer split stands: the wiki is untracked local working memory, and only its distilled output feeds committed project-local overlays in the target repo. One tightening falls out of the move: the consolidating agent never uses an editor tool on the store — it composes prose and hands it to wiki.py, which makes the CLI the sole writer mechanically rather than by convention.

One structural fact of this repository shapes the issue split. A new skill cannot land in pieces: CI runs evals/run_evals.py --structural on every pull request, which fails unless evals/cases/skills/wiki.json lands in the same commit as skills/wiki/SKILL.md, and scripts/tests/test_install.sh derives plugins/agy/skills/ from skills/*/ and fails unless the wiki link lands with it. Those three trees share no narrower parent, so the skill is one issue with a hint, alone in wave 1, where the width costs no parallelism. The two hook issues that follow are narrow and genuinely parallel; the documentation pass is the usual repository-wide issue at the end.

The previous plan.sidecar.json at the repository root was plan06, milestone 8 'Overlap the build wave loop' — closed on GitHub with all five issues closed, and its folio preserved at docs/plans/plan06-20260830-overlap-the-build-wave-loop.html. It is consumed, so overwriting it loses nothing.

Architecture

◇
current + proposed — compare the smallest meaningful system boundary, then state the operational change in plain language.

skills/wiki/scripts/wiki.py

The only writer: key, init, status, record, pattern, check. Resolves a target repository's primary toplevel the way `nova-ws` does, derives the project key from it, refuses a repository in eval mode, and never deletes anything.

~/.nova/wiki/<project-key>/

The data, outside every repository: project.json identity, raw/ write-once bundles, patterns/, index.md, logs.md, and skill-impact.md reserved for the proposer milestone. Root overridable with NOVA_WIKI_HOME.

skills/wiki/references/wiki-layout.md

The artifact contract the consolidating agent writes to: project key derivation and collision rules, and the exact shape of a raw bundle, a pattern page, an index row, a log line, and a skill-impact entry.

skills/wiki/SKILL.md

The dispatch contract: when consolidation runs, the opt-in rule, the single namespace-scoped documenter dispatch that writes only through the CLI, the mechanical gate, and the two standing boundaries.

skills/review-fix-loop/SKILL.md

The v1 hook point: the loop's exit consolidates on all three stop statuses, or does nothing at all when the project has no namespace.

skills/build/SKILL.md

The cheap hook point: an accepted wave records the integrator's evidence as a raw trace and never consolidates or gates on it.

agents/bodies/documenter.md

The writer, unchanged in v1 — dispatched with the resolved namespace as its ownership and the layout contract in its brief rather than given a new mode.

docs/adr/0019

The decision record: the global store with per-project namespaces, key derivation and collision refusal, the durability rules per layer, and the boundaries the wiki must not cross.

What changes

This changes what happens after work finishes, not how work is judged, and it puts the result outside the repository that produced it. Today a review-fix loop records each pass into `.nova/review-fix-loop.json`, stops on `converged`, `stalled`, or `exhausted`, and hands the branch over; the merged review JSONs die with the session, and an accepted `build` wave's integrator evidence dies with the merge. After this milestone both endings ask `wiki.py` one question — what is this repository's project key, does a namespace for it exist, and is this repository in eval mode — and, only when a namespace exists and eval mode is off, copy their evidence into an immutable raw bundle under `~/.nova/wiki/<project-key>/`. The loop then dispatches exactly one `documenter`, scoped to that namespace and handed the layout contract, which writes only through `wiki.py`; the orchestrator accepts the work on `wiki.py check` exiting zero rather than on prose. Nothing in the gate chain moves: the loop's bound and stop conditions, `tdd-guard`, the combined-GREEN merge gate, and every runtime agent's brief are untouched, no guard rule changes, and a project with no namespace sees none of it.

Current

Current architecture in words
  • code-review pass → loop_state.py record
  • loop_state.py record → builder mode loop (continue)
  • builder mode loop → code-review pass
  • loop_state.py record → branch handed to the human (converged / stalled / exhausted)
  • branch handed to the human → findings end with the session
  • build wave accepted → merge
  • merge → integrator evidence ends with the merge

Proposed

Proposed architecture in words
  • code-review pass → loop_state.py record
  • loop_state.py record → builder mode loop (continue)
  • builder mode loop → code-review pass
  • loop_state.py record → wiki.py resolves the project key and refuses eval mode (converged / stalled / exhausted)
  • build wave accepted → wiki.py resolves the project key and refuses eval mode
  • wiki.py resolves the project key and refuses eval mode → branch handed to the human (no namespace)
  • wiki.py resolves the project key and refuses eval mode → immutable raw bundle in the global namespace (namespace exists)
  • immutable raw bundle in the global namespace → one documenter, writing only through wiki.py
  • one documenter, writing only through wiki.py → patterns and index and logs, outside every repository
  • patterns and index and logs, outside every repository → wiki.py check
  • wiki.py check → branch handed to the human

Ship the persistent knowledge layer itself — one store outside every repository, namespaced per project, the contract that says what belongs in each layer, the offline CLI that is its only writer, and the skill's dispatch contract. Nothing consumes it yet; the two hook issues in wave 2 do that.

Where it lives. $NOVA_WIKI_HOME, defaulting to ~/.nova/wiki/, with one namespace per project at ~/.nova/wiki/<project-key>/. Note that ~/.nova/ does not exist today — this repository's home-level roots are ~/.local/bin, ~/.claude, ~/.codex, ~/.gemini, and ~/.agents — so this issue creates it; and NOVA_WIKI_HOME follows the only environment-variable precedent in the tree, NOVA_EVAL_TASK_DIR.

The project key. wiki.py key --repo <path> is a subcommand of its own so the derivation is directly inspectable and directly testable:

1. Resolve the target repository's primary toplevel exactly as nova-ws does — through the .jj/repo indirection for a secondary jj workspace, through the first git worktree list --porcelain entry for git — so every build per-issue workspace of one repository answers with one key. 2. If that repository has an origin remote, the key is the normalized remote: scheme, user, and port stripped, a trailing .git stripped, lower-cased, host and path segments joined with dashes — github-com-anvil008-nova. git@github.com:anvil008/nova.git and https://github.com/anvil008/nova must collapse to the same key. 3. With no remote, the key falls back to <toplevel-basename>-<first 8 hex of the sha256 of the resolved absolute toplevel>. 4. Either way the key is reduced to the character class nova-ws already enforces for a key part — [a-z0-9][a-z0-9-]*, every other character written as a dash and runs collapsed, no slash — so a wiki key and a workspace key obey one spelling rule and neither can carry a path separator. 5. Collisions are refused, not resolved. project.json in the namespace records projectKey, source (remote or path), the origin or toplevel it was derived from, and createdAt. Every later command re-resolves and compares; a mismatch exits non-zero naming both the recorded and the resolved source. Renaming or retiring a namespace is a human act, like entering eval mode.

Layout, created by wiki.py init inside the namespace:

- project.json — the identity record above. - raw/<id>/ — one immutable bundle per recorded run: manifest.json (id, kind, recordedAt, summary, and every copied file with its sha256) plus the copied evidence files. Write-once. - patterns/<slug>.md — one failure mode or successful strategy per page, with a dated Evidence section citing raw ids. Append-only prose. - index.md — the catalog, one row per pattern page with its occurrence count and last-seen date. - logs.md — the chronological evolution log, one appended line per write. - skill-impact.md — the accept/reject audit trail for skill-change proposals. v1 creates the file and documents its format in the reference; nothing writes an entry yet.

CLI. key, init, status, record, pattern, check. Every subcommand takes --repo <path> (default the working directory) naming the target repository, from which it resolves the key and reads that repository's .nova/eval-mode.json: a repository in eval mode is refused, which is what keeps a benchmark run from writing into or reading from a persistent namespace. --namespace <dir> names a namespace directory directly, bypassing both resolutions, for the shipped demo and the tests. No subcommand deletes anything — there is no reset and no rollback — and check proves the raw layer's immutability by re-hashing every recorded file against its manifest. The tests must drive NOVA_WIKI_HOME at a temporary directory; a suite that writes into the developer's real home is a defect.

skills/wiki/references/wiki-layout.md — the artifact contract the consolidating agent writes to, per ADR 0009: key derivation and collision rules, and the exact shape of a raw bundle, a pattern page, an index row, a log line, and a skill-impact entry, plus the rule that a pattern page accumulates evidence and is never rewritten to say something different.

skills/wiki/SKILL.md — the dispatch contract: the canonical ADR-0007 orchestrator paragraph, one line on what this orchestrator owns, the opt-in rule (no namespace means no record, no dispatch, and no tokens spent), the single documenter dispatch whose ownership is the resolved namespace path and which writes only through wiki.py, never with an editor tool, wiki.py check as the completion gate, an offline demonstration over skills/wiki/examples/sample-namespace, and the two standing boundaries — runtime agents (specifier, builder, reviewer, integrator) are never given the wiki, and project patterns feed project-local overlays in the target repository only, while Nova's shared skills/ continue to change through evidence-backed pull requests gated by the eval tiers.

Also in this issue, because CI couples them: evals/cases/skills/wiki.json (three or more positive prompts, two negatives naming their owner, one dialogue eval — run_evals.py --structural fails if the case and the SKILL.md do not land together) and the plugins/agy/skills/wiki symlink (scripts/tests/test_install.sh derives that directory from skills/*/ and fails if it drifts). That coupling across skills/, evals/, and plugins/ is why the ownership hint is **; the issue is alone in wave 1, so the width costs no parallelism.

Out of scope: the skill proposer, validation-gated skill updates, any write to skill-impact.md, cross-project or shared namespaces, and any change to an agent body, agents/handoff.md, or a guard rule — read-only investigation confirmed no guard change is needed, since build-guard has no outside-repository write rule and tdd-guard's sealed-path check returns false outside the repository.

R-01A global store is per machine and per user, so knowledge still does not reach a teamrepository owner adopting the wiki

Likelihood high · impact med

MitigationThe move already buys the larger win: every clone and every `build` workspace of one project now shares one namespace instead of fragmenting per checkout, and the paper's ablation holds structurally because the store is outside every repository. `NOVA_WIKI_HOME` makes the root relocatable onto synced or shared storage without a code change, and `wiki.py status` reports `present: false` and exits zero wherever a namespace is missing. A real export/import path stays named as proposer-milestone work in ADR 0019's consequences rather than assumed away.

R-02Two projects resolve to one key, or a renamed remote orphans a namespaceWikiStore builder

Likelihood med · impact med

MitigationIdentity is recorded, not inferred: `project.json` stores the source the namespace was created from, every command re-resolves and compares, and a mismatch is refused by name — naming both the recorded and the resolved source — instead of silently sharing or silently forking. `wiki.py key --repo <path>` prints the key and its source, so the answer is inspectable before anything is written, and renaming or retiring a namespace stays a human act.

R-03An eighteenth skill description pushes routing below the 77% rank-1 floorWikiStore builder

Likelihood med · impact med

MitigationThe case ships in the same pull request as the skill because CI requires it, and both free tiers are acceptance tests on that issue: `--structural` for coverage and description collision, `--min-rank1 77` for the floor. The description is written to sit away from `docs` and `research` — persistent knowledge from finished runs, explicitly not user-facing documentation — and `run_evals.py` reports a collision at 50% before it fails at 75%.

R-04Wave 1 is wide and wave 1 is one issue, so a bad split cannot be recovered by parallelismbuild orchestrator

Likelihood med · impact med

MitigationThe width is forced by CI coupling across `skills/`, `evals/`, and `plugins/`, not chosen, and it is spent where it is free: wave 1 has one issue, so nothing is serialized behind it. The issue is bounded to a store, a contract, and a skill file with no consumers — the two hook issues in wave 2 are what wire it in, and either can bounce back to its builder without disturbing the other.

R-06The documenter is asked to do root-cause work outside its docs-only jobwiki skill

Likelihood med · impact med

MitigationThe brief hands it the loop's own verified findings — file, claim, failure scenario, and the independent verification evidence that substantiated each — rather than a codebase to diagnose, so the work is grouping and citing rather than debugging. It writes only through `wiki.py`, never with an editor tool, and `wiki.py check` is the gate. A dedicated mode or agent is deferred to the proposer milestone, where the job genuinely changes.

R-07The store sits outside every repository, where a harness sandbox or permission prompt may block the writeoperator adopting the wiki

Likelihood med · impact med

MitigationNova's own gates were checked read-only and do not stand in the way: `build-guard` has no outside-repository write rule, its only path denials being the eval-mode marker and RAM-backed build target directories, and `tdd-guard`'s sealed-path check returns false for anything outside the repository. That leaves only the harness's own permission model, and every write goes through a single `wiki.py` Bash invocation rather than editor tools, which is one surface an operator can allow once and the documenter contract already assumes.

R-05Consolidation spends an extra agent dispatch on every loop endingreview-fix-loop orchestrator

Likelihood med · impact low

MitigationIt runs once per loop rather than once per pass, and only for a project that opted in by creating a namespace. The record step is mechanical and free; only the pattern-writing pass costs tokens, and its ownership is one directory.
